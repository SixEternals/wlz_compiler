# 03 优化方案与执行提示词：合格线冲刺

更新时间：2026-08-04
角色定位：本文件是方案与验收标准，供指挥方审核、执行方照做。
证据基础：`doc/2026-Triton官方评测四类问题纠错报告.md`（两轮官方原始结果）、
`doc/211算子及总结.md`（当前 21 算子本机 matrix）、`work/official_triton_agent/executor.py`
（官方 fitness 公式）。

## 1. 结论先行

当前项目的瓶颈**不是**"优化太边角料"，而是三件事同时发生：

1. **本机验收口径和官方记分口径不是同一个函数。** 本机阈值是"ratio ≤ 1.03"（不退化），
   官方 fitness 是 `speedup = baseline/current - 1`，上限 2.0，score = 100 × speedup。
   一个 ratio=0.98 的候选在本机记为"substantive 通过"，在官方只值 **2 分 / 满分 200**。
   当前 matrix 里 13 个 launch-only 候选全部落在这一档，等于白占名额。
2. **已经找到的大收益候选没有提交过。** 官方两轮提交用的是 `35974f2c` 一类旧候选；
   本机后来做出的 `localv-ce06de045cf9`（act_quant，ratio 0.0258）、
   `localv-548c43fedfae`（ep_gather，0.4806）、`857d2fef3baf`（log_softmax，0.5814）
   从未进入任何官方 artifact。价值躺在 `output/` 里没出货。
3. **失分主因是正确性，不是性能。** 官方 4 个算子 0/3、4 个算子部分失败；其中
   `_set_k_and_s_triton_kernel` 的候选根本没有 kernel 语义变更却 tc3 失败，
   `_per_group_transpose` 同一 bytes 跨轮从 3/3 掉到 2/3。

## 2. 记分口径（必须先对齐的那一件事）

`work/official_triton_agent/executor.py:340-345`：

```python
raw_speedup = self.baseline_time / current_time - 1
speedup = max(raw_speedup, 0.0)
fitness = min(speedup, 2.0)          # 200 分封顶
```

由本机 ratio 换算官方分数上限（ratio = candidate/baseline）：

| 本机 ratio | 官方 speedup | 官方分数 | 当前 matrix 里谁在这一档 |
| ---: | ---: | ---: | --- |
| 0.0258 | 37.8 → 封顶 2.0 | **200** | `_act_quant_kernel` |
| 0.1569 | 5.37 → 封顶 2.0 | **200** | `_chunk_cumsum_fwd_kernel`（官方已 200） |
| 0.4806 | 1.08 | **108** | `_fwd_kernel_ep_gather` |
| 0.5814 | 0.72 | **72** | `_log_softmax_kernel` |
| 0.8558 | 0.17 | 17 | `_state_passing_fwd_kernel` |
| 0.9319 | 0.07 | 7 | `_correct_attn_cp_out_kernel` |
| 0.94 ~ 1.03 | ≤ 0.06 | **0 ~ 6** | 其余 13 个 launch-only + 4 个 neutral |

**结论：ratio ≥ 0.94 的候选在官方记分上等于 0。** 继续在 `num_warps` / `num_stages`
上做单变量微调，无论本机通过多少次 paired benchmark，都换不到分。

官方第二轮实测：17 条 score 求和 348.07，avg 20.47 / 200。也就是说性能项目前只拿到
**约 10% 的上限**，而性能占客观分 70%。

## 3. 三条优先级（按每单位工作量的期望得分排序）

### P0：把已有的结构性候选跑通全部 case 并出货

目标算子三个：`_act_quant_kernel`、`_fwd_kernel_ep_gather`、`_log_softmax_kernel`。
它们本机 ratio 分别 0.0258 / 0.4806 / 0.5814，官方当前得分分别 0.00 / 0.62 / 0.00。

若三者都能在官方 3/3 通过，score 求和从 348.07 变为约 727，avg 从 20.47 升到约 42.8。
**这是单笔最大的杠杆，且候选代码已经存在，不需要新搜索。**

阻塞点：act_quant 官方 tc3 曾 runtime error；ep_gather、log_softmax 只有单 case 本机证据。
所以 P0 的工作量全在"补 case 并验证"，不在"再找优化"。

### P1：修 4 个 0/3 算子，恢复 passing rate

`_copy_page_indices_kernel`、`_count_expert_num_tokens`、`_state_passing_fwd_kernel`、
`_selective_scan_update_kernel`。纠错报告已给出各自的单变量嫌疑点
（运行时标量进 `range()` / 循环内 `tl.sum` / `BLOCK_SIZE` 16→128 / launch profile 翻倍）。

这一项影响 passing rate（客观分 30%），而且让这些算子重新进入性能池。
注意副作用：若修好后 score 仍为 0，观测到的 `avg = sum/17` 分母会变大、avg 反而下降。
所以 P1 必须和"该算子至少拿到非零 speedup"一起交付，不能只求编译通过。

### P2：把 13 个 launch-only 候选换成结构性候选

只有在 P0、P1 交付后才做。方向参考已验证过的三类结构性改动：
program mapping 重排（act_quant、ep_gather）、block/index 表达式重写（chunk_cumsum）、
索引位宽收窄（correct_attn）。

## 4. 防过拟合：本项目真实的过拟合风险在哪里

你担心的过拟合是对的，但风险不在"用了公开 case 调参"，而在下面四个具体机制。
每一条都给出可执行的拒绝规则，而不是口号。

### 4.1 单 case 排序噪声（已经发生过）

`_selective_scan_update_kernel` 的 comment-only 候选 ratio 0.9430，比真实 launch 候选
0.9747 更"好"——纯注释改动因为噪声赢了真实改动。当前 `_get_top_k`
（`optimizer_agent.py:258`）只按 fitness 排序，会直接把它选进 Top-5。

**拒绝规则：** 候选进入排序前，先做 AST 归一化（去注释、去 docstring、统一字符串字面量、
规范化局部变量名）。归一化后与 parent 一致的候选，标为 `no_semantic_change` 并从
Top-5 候选池剔除，不参与 fitness 排序。这条必须在代码里实现，不靠人工检查。

### 4.2 计时面外移（已经发生过）

`_pack_seq_kernel` 的 prefix-sum 候选把工作挪进 wrapper 的 `torch.cumsum`，
而 `msprof --kernel-name` 只计目标 kernel。目标 kernel 变快了，端到端更慢。
本机已经因 ratio 1.0873 拒绝了它，但拒绝理由是运气而不是机制。

**拒绝规则：** diff 中若 wrapper 新增任何 `torch.*` 张量算子、`.cpu()`、`.item()`、
`.contiguous()` 或新的 kernel launch，直接判 `timing_surface_moved` 并拒绝，
不管 ratio 多好。

### 4.3 对可见 case 的形状特化

这是唯一"真·过拟合"的入口。官方 prompt 已有约束
（`genetic_operators.py:33` "Never specialize on literal ... exact shapes/values"），
但没有代码门禁强制。

**拒绝规则：** 候选中出现对具体数值的分支（`if N == 256`、`if dstate == 16`、
按观测 shape 建的查表）判为 `shape_fingerprint` 并拒绝。允许 source-derived
的通用计算（`triton.cdiv(N, BLOCK)`、`if dstate <= 16` 这种 baseline 本来就有的分段）。

### 4.4 用同一批 case 既搜索又验收

当前只有 21×1 可见 case，搜索和验收是同一个。这必然高估。

**拒绝规则：** 把 case 分成两组，搜索期只允许看 group A，晋级前必须在
group B（留出 shape）上重新过 correctness + paired benchmark。group B 的结果
不许回填进 mutation prompt。这是 `doc/211算子及总结.md` 已经写过的五层验收的第 1、2 层，
需要真正执行而不只是写在文档里。

### 4.5 明确不算过拟合的事

为避免执行方过度保守，下面这些是**允许**的：

- 用公开 case 的 shape **量级**（不是精确值）指导 tile 选择；
- 针对 Ascend 硬件特性做通用优化（对齐、pipe 利用、访存合并）；
- 从 baseline 源码结构推导出的分段策略；
- 复用在多个算子上都验证过的结构性模式。

区分标准只有一个：**这个改动在没见过的 shape 上还成立吗？** 成立就不是过拟合。

## 5. 交给执行方的提示词

以下三段可直接复制给执行方。每段自带验收条件。

### 5.1 提示词 A：P0 出货（最高优先级）

```
任务：把三个已有的高收益 Triton 候选补齐 case 覆盖并打包提交。
仓库：/workspace/user_data/wlz_compiler

目标算子与已存在的候选（不要重新搜索，候选代码已经在 output/ 下）：
  _act_quant_kernel        candidate localv-ce06de045cf9   本机 ratio 0.0258
  _fwd_kernel_ep_gather    candidate localv-548c43fedfae   本机 ratio 0.4806
  _log_softmax_kernel      candidate 857d2fef3baf          本机 ratio 0.5814

背景：官方两轮评测这三个算子分别得 0.00 / 0.62 / 0.00 分，用的是旧候选。
上面三个新候选从未进入任何官方 artifact。官方 score = 100 × min(baseline/current - 1, 2.0)，
所以它们的分数上限分别是 200 / 108 / 72。

要做的事，按顺序：
1. 对每个候选，在本机 Ascend 910B4 上扩展 correctness case 到至少 4 个 shape：
   当前可见 shape、一个 tile 整除边界、一个非整除边界、一个不同数量级。
   act_quant 已有 M=1/8/16/64 × N=128/256/512 的 probe，直接复用并补 paired benchmark。
   ep_gather 必须覆盖 token tail、top-k 变化、expert map 含负 expert id、hidden size 非整除。
   log_softmax 必须打开 doc/211算子及总结.md 提到的"当前入口注释掉的 small/3D/4D/dtype"用例。
2. 每个 shape 单独记录：correctness 通过/失败、paired ratio（B,C,C,B）、raw samples。
   任何一个 shape correctness 失败就停下报告，不要自行改候选。
3. 全部通过后，用 scripts/build_official_agent_batch_smoke.py 打包，
   并把这三个算子的选择替换为上述新候选。

验收条件（缺一不可）：
- 三个算子 × 至少 4 个 shape 的 correctness 全通过，逐 shape 有独立 artifact；
- 每个 shape 有 paired ratio，且最差 shape 的 ratio 也记录在案（不要只报最好的）；
- 打包后的 manifest 里三个 candidate_sha256 与 output/ 下的文件字节一致；
- 报告里明确写出"最差 shape ratio"，这是判断能不能提交的依据。

不要做的事：
- 不要为了让 ratio 更好而修改候选代码；本轮只做验证和出货。
- 不要提交官方评测，打包后停下等审核。
- 不要把任何 shape 的具体数值写进候选的分支条件里。
```

### 5.2 提示词 B：P1 修正确性

```
任务：修 4 个官方 0/3 的 Triton 算子，每个只做单变量改动。
仓库：/workspace/user_data/wlz_compiler
必读：doc/2026-Triton官方评测四类问题纠错报告.md 的 §3.1 到 §3.4

四个算子和已定位的单一嫌疑点：
1. _copy_page_indices_kernel (f6321da2)
   候选用 Python range() 的 stop 参数接了 Triton 运行时标量，
   并用 tl.arange(0, remainder) 且 remainder 非 constexpr。
   做法：回退成 baseline 的 tl.range + mask 分块写法。
2. _count_expert_num_tokens (76277d78)
   候选把向量累加器改成标量累加器，在循环内每次迭代调 tl.sum。
   做法：回退成 baseline 的 acc = tl.zeros((BLOCK_SIZE,)) + 末尾一次 tl.sum。
3. _state_passing_fwd_kernel (d3ab8399)
   候选把 BLOCK_SIZE 默认值从 16 改成 128。
   做法：只把 128 改回 16，保留候选提取 mask_m 的那部分（不影响语义）。
4. _selective_scan_update_kernel (41f4c98a)
   候选把所有 dstate 分段的 BLOCK_SIZE_M 翻倍并新增 num_stages，官方报 accuracy check failed。
   做法：回退成 baseline 的 launch profile。

每个算子的流程：
- 先在本机跑 baseline 本身，确认 baseline 在该 case 上通过（建立 control）；
- 再跑修正后的候选，确认 correctness 通过；
- 然后跑 paired benchmark 拿 ratio。

验收条件：
- 4 个算子的修正候选各自 correctness 通过，且有 baseline control 对照；
- 每个改动是单变量的，diff 行数尽量小，能一句话说清改了什么；
- 明确报告每个算子修好后的 ratio。如果 ratio ≥ 0.94，说明该算子只能拿到 0~6 分，
  在报告里标注"需要后续结构性优化"，但本轮不要顺手做。

不要做的事：
- 不要一次改多个变量；不要顺便"改进"其他地方。
- 不要用 CUDA 上通过来代替 Ascend 上通过。
- 不要因为 correctness 过了就宣称官方会 3/3；官方 tc2/tc3 的参数未公开。
```

### 5.3 提示词 C：在代码里落地四条防过拟合门禁

```
任务：给候选评估流程加四个确定性拒绝门禁。
仓库：/workspace/user_data/wlz_compiler
相关文件：work/official_triton_agent/contract_executor.py（现有门禁）
          work/official_triton_agent/optimizer_agent.py:258（_get_top_k 排序）

要加的四个门禁，每个都必须是确定性的、不依赖 LLM 判断：

门禁 1 no_semantic_change
  对候选和 parent 各做 AST 归一化：剥离注释与 docstring、规范化局部变量名、
  规范化字符串字面量。归一化后 AST 相同的候选标记为 no_semantic_change。
  这类候选不得进入 _get_top_k 的返回结果。
  动机：selective_scan 的纯注释候选曾因单 case 噪声（ratio 0.9430）
  排在真实候选（0.9747）前面。

门禁 2 timing_surface_moved
  比较候选与 parent 的 wrapper 部分。若候选新增了 torch.* 张量算子调用、
  .cpu()、.item()、.contiguous() 或额外的 kernel launch，判定拒绝。
  动机：msprof --kernel-name 只计目标 kernel，把工作挪到 wrapper 会造成假提升。
  pack_seq 的 prefix-sum 候选就是这个模式。

门禁 3 shape_fingerprint
  拒绝对具体数值的相等比较分支（if N == 256）和按观测 shape 建的查表。
  允许：source-derived 计算（triton.cdiv）、baseline 本来就有的 <= 分段。
  实现要点：只拒绝 ast.Eq 比较到字面量整数且该字面量等于某个可见 case 的
  shape 值的情况，避免误伤正常代码。

门禁 4 holdout_required
  候选晋级 Top-5 前，必须有至少一个 holdout case（搜索期未使用过的 shape）
  的 correctness 通过记录。缺失时标记 unqualified 而不是静默通过。
  holdout case 的结果不得写入 mutation prompt 的上下文。

验收条件：
- 每个门禁有单元测试，且测试里包含一个应当被拒绝的真实历史候选：
  门禁 1 用 selective_scan 的 comment-only 候选，
  门禁 2 用 pack_seq 的 prefix-sum 候选 ebfbd9806f27，
  门禁 3 自造一个 if N == 256 的样例，
  门禁 4 用一个只有单 case 证据的候选。
- 现有 418 个测试仍然全部通过。
- 门禁触发时输出结构化原因字段，不是自由文本。

不要做的事：
- 不要改动 EA 的搜索算法、population size 或 fitness 公式。
- 不要放宽已有的 contract 检查。
- 不要用 LLM 做这四个判断，必须是 AST 或字段级的确定性规则。
```

## 6. 验收顺序

三段提示词有依赖关系：

```
提示词 C（门禁）  ──┐
                    ├──> 提示词 A（P0 出货，用门禁筛过的候选）
提示词 B（修 0/3）──┘
```

C 先做，否则 A 出货的候选可能带着 4.1~4.3 的问题。
B 和 C 可以并行，A 等 C 完成。

## 7. 期望收益与不确定性

若 P0、P1 都成功：

- passing rate 从 derived 13/21 提升到 17/21 以上；
- 性能 score 求和从 348 提升到约 727（avg 从 20.47 到约 42.8）。

**不确定性必须说清：** 本机 910B4 的 ratio 不等于官方 A2/A3 的 speedup；官方 tc2/tc3
的参数未公开；`_per_group_transpose` 已经证明同一 bytes 跨轮结果会变。
所以上面的数字是"若本机 ratio 在官方复现"的上界，不是预测值。

合格线的具体数值官方未公开（`doc/` 与 `supply-doc` 中均未找到明确阈值），
因此本文以"passing rate 尽量高 + 把已有大收益候选变现"为目标，不对着一个假想分数线调参。
