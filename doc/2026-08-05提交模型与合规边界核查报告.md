# 提交模型与合规边界核查报告

日期：2026-08-05  
范围：2026 编译系统挑战赛“基于进化算法的 Triton 自动优化系统”

## 结论

本赛题存在两条不同的交付链，不能把它们混为“传 ZIP”或“平台跑活 agent”的单选题。

| 目的 | 当前实际提交物 | 平台行为 | 结论 |
| --- | --- | --- | --- |
| 线上测评、获得成绩 | 根目录含 `output/` 的候选 ZIP | 读取/评测候选输出；历史上传 agent 源码包时没有运行 `main.py` | **冻结候选 ZIP** |
| 初赛/决赛作品与合规审查 | GitLab 项目中的 agent 工程源码、设计文档 PDF，初赛还包括 MP4 | 官方技术方案要求代码托管和指定版本；老师已确认 PDF 放 GitLab 根目录 | **提交 agent 工程及材料** |

因此，当前 CourseGrading 表单不会在线执行 Prompt Runtime 或进化循环；它评测的是 ZIP 内已经冻结的候选代码。与此同时，竞赛规则要求作品本体是 agent 工程，且候选必须由 agent 经统一接口产生，不能人工改写 Triton 代码。ZIP 测评成功不等于自动满足后者。

## 直接证据

### 1. 当前线上测评是候选 ZIP，不是运行 ZIP 内 agent

[P1提示词工程成果审核与提交交接.md](P1提示词工程成果审核与提交交接.md) 第 5 节记录了实际表单行为：

- 上传入口要求 ZIP 根目录包含 `output/`；
- 曾上传平铺的 Agent 源码包，平台返回 `cp: cannot stat '/coursegrader/submit/output'`；
- 平台没有执行包内的 `main.py`；
- 该表单只能验证“Prompt v2 产出的候选”的 Ascend 结果，不能验证 Prompt Runtime 的在线执行。

同一文档第 6 节给出了实际投递前的打包要求：生成 `output/<kernel>/...`，最多保留 5 个版本，校验 ZIP、路径、秘密、大小和 SHA-256 后再上传。

前两轮线上结果也与此一致：两轮均由 `scripts/build_official_agent_batch_smoke.py` 打包为 `organizer-save-results-v1`，页面返回 `AC(47/63)`、`AC(46/63)`，见 [2026-Triton官方评测四类问题纠错报告.md](2026-Triton官方评测四类问题纠错报告.md) 第 2.1 节。2026-07-21 的后续提交页面显示 `AC(55/63) | 20/21 kernels | 提交21/21`，见 [阶段2导向报告之后至官方结果离线闭环工作报告.md](阶段2导向报告之后至官方结果离线闭环工作报告.md) 第 5.3 节。

### 2. 正式作品和规则要求 agent 工程

官方技术方案第 4 条要求在提供的 agent 框架上实现进化算法；评分阶段对每个算子最多运行 20 分钟或 20 万 token。第 5 条要求 agent 经统一接口返回至多 5 个候选。第 11 条把 `agent 工程源码` 和 PDF 设计文档列为初赛、决赛提交物；第 16 条说明评测系统可从代码托管平台取得指定版本。

本地原始 PDF：
[技术方案 PDF](sources/official_compiler2026_archive/compiler2026-main/2026年全国大学生计算机系统能力大赛编译系统设计赛-编译系统挑战赛-基于进化算法的Triton自动优化系统-技术方案.pdf)

该 PDF 同时明确：

- 待优化 Triton 代码应通过 agent 变换和搜索；
- 参赛队不得手动修改 Triton 代码；
- 需要使用指定环境与接口，不能改变接口调用方式。

用户提供的老师答复进一步确认：进行线上测评取得成绩后，设计文档放在 GitLab 根目录即可。

### 3. 平台操作说明确认 GitLab 链接是评测入口

用户补充的官方“作品提交方式”原文为：

> 要求在 GitLab 项目内开发，并通过 GitLab 项目链接提交评测。注意仅支持 HTTPS，不支持 SSH。

同一说明要求队伍自行创建项目并加入成员；建议项目名为 `Compiler2026-X`，项目描述写明队伍 ID、队伍名称和学校名称。队伍账号在官网跳转后的比赛平台修改密码后，可通过 GitLab 图标使用该队伍账号登录。

这确认了 GitLab 不是仅用于存档：它是正式评测申请所引用的工程位置。它没有推翻当前 CourseGrading 表单接收 `output/` ZIP 的实测事实，而是进一步证明两条交付链都必须维护。

## 可执行的提交方式

### A. 为线上成绩提交

1. 通过 agent 生成候选，保留父代、prompt/模型、token、时间、代码 hash 和 gate 结果。
2. 不在生成后手工编辑候选 Triton 源码。
3. 打包为一个 ZIP，归档根目录必须含 `output/`；按 21 个 kernel 槽位布局，每个槽位最多 5 个候选。
4. 上传该 ZIP 到 CourseGrading，保存 ZIP SHA-256、页面快照与原始结果。

这是一份冻结候选的评测投递。它不要求、也不会触发平台运行 ZIP 内的 agent。

### B. 为正式作品和合规提交

GitLab 项目根目录应至少保留：

- agent 工程源码及可复现的依赖/启动说明；
- `设计文档.pdf`；
- 初赛要求的 MP4（若当前平台要求在仓库交付）；
- 生成 provenance：候选 hash、父代、模型、prompt 标识、token、时间、gate 与 ZIP SHA-256 的绑定记录；
- 第三方代码和 AI 使用说明。

项目使用 HTTPS 地址提交评测，不使用 SSH 地址；项目名称可按官方建议使用 `Compiler2026-X`，并在项目描述中填写队伍 ID、队伍名称和学校名称。

正式文档应说明线上 ZIP 是 agent 运行后产生的冻结输出，而不是把 ZIP 描述成“平台运行了在线 agent”。

## 对当前策略的影响

原先“若是冻结 ZIP、且允许离线候选”的前半句已经成立：当前线上测评确实上传冻结候选 ZIP。后半句必须收紧为：

> 可以离线生成候选后上传，但每个待提交候选必须可追溯到合规的 agent 调用；不能把表单不执行 `main.py` 误解为允许人工写候选。

所以 Luna 可以执行“功能保底 + 不同构造槽位”的紧配方，但必须把以下内容作为提交闸门：

1. **类型真不同**：对每个候选保存相对父代的结构化 diff 和 mutation kind；仅改注释、报错字符串或格式的候选直接拒绝。
2. **ratio 太好要疑**：异常速度结果只能标为待复核，不能作为入选依据；先确认正确性、计时口径与可重复性。
3. **holdout 不污染**：隐藏/保留用例、精确输入、原始日志不进入 prompt、候选选择或人工改写环节。
4. **agent 溯源完整**：每个候选有模型、prompt 标识、token、父代、时间、代码 hash；生成后禁止手改。
5. **归档正确**：ZIP 根含 `output/`，21 槽位完整，单槽位不超过 5 个版本，并保存 SHA-256。

结构性 v2 和已被 T5/T6 门禁拦住的 8 个问题算子，仍不应混入这次只求功能覆盖的提交批次。

## 未消除的不确定性

官方技术方案描述了代码托管平台取得指定版本的正式机制，而当前 CourseGrading 表单的实测行为是上传候选 ZIP。两者说明的是不同层面的交付，现有证据不能证明该表单会运行 GitLab 中的 agent，也不能证明最终复核只看 ZIP。

因此最稳妥做法是始终同时维护两套可互相核验的证据：用于计分的冻结 `output.zip`，以及 GitLab 根目录中的 agent 源码、`设计文档.pdf` 与候选溯源记录。
