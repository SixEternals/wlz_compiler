# 最近成果：本机 910B4 21 算子资格闭环

更新时间：2026-08-03  
证据范围：`local_ascend_910b4_currently_visible_cases_not_official`

## 结论先行

当前 checkout 的 21 个公开算子均已完成一条可复核的本机资格闭环：

- 每个算子都有一个非 baseline candidate source；
- 当前可见的 `1` 个 test case 中，baseline 和 candidate 都以真实 Ascend 910B4 解释器返回 0；
- 每个 candidate 都完成同 case、同 device、同频率的 `B,C,C,B` 四次 `msprof` 配对；
- candidate median / baseline median 的最坏 case ratio 均不超过 `1.03`；
- 资格矩阵：`qualified=21/21`。

当前共有 30 个新格式 paired sidecar：22 个通过本机阈值，8 个回归候选被拒绝。
矩阵选中的 21 个 candidate 中，14 个有真实 kernel/launch 变化，7 个仍只是注释、格式或
等价表达式；后者只用于验证不退化，不计入成功优化策略。

这不是官方成绩。当前数据集是 `21 x 1` 可见 case，官方 case 2/3 和 A2/A3 结果仍为 unknown。

## 失败经验已保留

失败候选没有从输出目录删除，矩阵只选择通过 threshold 的 candidate：

- dequant 的 slice/grid、num_warps=4、num_stages=1 和 comment-only probes 分别出现约 `1.096`、
  `1.042`、`1.064`、`1.043` ratio；最终 `num_warps=1` 才通过；
- count 的 `BLOCK_SIZE` cap 1024 -> 2048 ratio `1.079`，512 才通过；
- trtllm 的 num_warps=4 ratio `1.036`，num_warps=2 为 `1.000`；
- per-group transpose 的 `BLOCK_SIZE_K=8 -> 16` 单变量 probe ratio `1.468`，已拒绝并继续选用
  原 format-only 资格候选；
- chunk-state 首次 profile 因 Ascend `_mix_aic` 名称未被旧 parser 识别，原始目录以
  `failed-parser-exact-name` 保留，修复 parser 后重跑通过；
- per-token 一次 benchmark 与手工启动的 correctness 短暂重叠，整套 sidecar/raw evidence 以
  `invalid-overlap` 保留并未计入矩阵，随后独立重跑通过。
- pack-seq 的 prefix-sum 候选 `ebfbd9806f27` 在额外 `B=1,D=7` 以及含零长度、三维输入的
  `B=5,D=15` 上通过 correctness；但首个边界 case 的目标 kernel paired ratio 为
  `1.0873364743`，超过 `1.03` 后 fail-fast，因此已拒绝且未替换现有候选。它还在
  wrapper 中新增 `torch.cumsum`，当前按 kernel-name 计时不覆盖这个额外 NPU op，所以
  即使目标 kernel 本身变快也不能据此晋升。诊断证据位于 `output/overfit-probes/`。

这些失败经验可以作为后续 Experience System 的真实 seed，但必须携带算子、source/test hash、
设备/频率、输入 seed、候选变更类型和失败阶段，不能只保存一个自然语言“策略失败”。

## 防过拟合复盘

当前 `21/21` 只能回答“这些候选在当前 checkout 的单个可见 case 上是否不慢于 3%”。
它不能回答以下问题：其他 shape/dtype/layout 是否正确，性能排序是否稳定，或在 A2/A3
上是否仍然有效。为避免 Agent 把公开 case 当成唯一目标，后续候选应分五层验收：

1. **候选生成与扩展 case 分离**：LLM 只看算子合同和必要的公开信息；本地边界/固定
   seed case 用于选后审计，不把逐 case 答案回填到 mutation prompt。
2. **正确性覆盖**：优先覆盖至少 3 个可重放 input ID/seed，包括当前 shape、tile/divisibility
   边界和一个不同 shape bucket；所有 case 逐个通过 oracle 才能进入性能测量。当前还没有
   21 算子的完整扩展 case 集，因此不声称这一层已完成。
3. **计时边界不变**：候选新增 wrapper 级 NPU op、host sync 或预处理时，必须计入同一评测
   surface；不得通过把工作移出 `--kernel-name` 捕获范围制造假提升。
4. **分布而非单点**：每个 input 先 warmup，再保存重复样本及 p50/p10/p90；当前每个 role 只有
   2 次的 `B,C,C,B` 是低成本 qualification，不是高置信度稳定性结论。正确性、性能和
   determinism 分开记录。
5. **按条件复用**：性能/Experience 的最小 key 至少是 `(operator, shape/signature,
   dtype/layout, normalized_code_hash, executor_kind, environment_fingerprint,
   input_set_id/seed)`。单 shape 最优 config 不升级为跨 shape 规则，910B4 结论不升级为
   A2/A3 性能经验。

### 开源项目参考

以下只借鉴评测和数据边界，不直接复制 CUDA 实现：

- Triton commit `4b65f412cda233c3fe1f05e10b48e622b725d4b0`：
  `python/triton/runtime/autotuner.py:187-244` 将 target/code/environment/tuning key/config 和运行时
  key/dtype 纳入 cache 边界；`python/triton/testing.py:267-337` 使用 warmup、repetition 和 quantile。
- TritonBench commit `fbc056a9d7185f84cf9c66bd27f42112398934fc`：
  `tritonbench/utils/triton_op.py:853-980` 支持多 input ID、等距/随机抽样及可记录 seed；
  `tritonbench/utils/triton_op.py:1122-1165` 对每个 input 分别跑 backend。
- KernelBench commit `423217d9fda91e0c2d67e4a43bf62f96f6d104f1`：
  `src/kernelbench/eval.py:583-637,727-848` 将 correctness 和 performance 分阶段，多个确定性 seed
  全部正确后才测性能；`src/kernelbench/timing.py:201-279` 显式控制 warmup、重复和首轮丢弃。
- PyTorch commit `9926bced18cef9b11906b834988b2dfd3c6a84e1`：
  `benchmarks/dynamo/common.py:2319-2556` 先检测 reference 自身的非确定性，再多次运行优化结果
  做 accuracy 判定。

这些设计支持的不是“多跑几次就不过拟合”，而是将配置、输入、设备、代码和量测分布绑定在
同一条可重放证据上。本项目的 Experience System 只应记住这种带条件事实，不应记住
“某个 BLOCK_SIZE 普遍更好”。

## 证据边界

- correctness producer 只证明当前 checkout 的可见 tests；不推断官方隐藏 case。
- paired runner 固定 `B,C,C,B`，对未自带 `torch.manual_seed` 的 test 注入并记录 `input_seed=0`。
- runner 只接受精确 operator 名或 Ascend 的 `_mix_aic/_mix_aiv` 后缀；profile 缺字段会 fail-closed。
- `vllm.triton_utils` shim 只在 source/test 明确引用该模块时生成，不代表仓库安装了 vllm。
- comment-only/format-only candidate 只证明“不超过本机 baseline 3%”，不应进入“成功优化策略”统计。
- 本机真实性能证据不能替代官方 A2/A3 functional pass、latency、speedup 或最终排名。
