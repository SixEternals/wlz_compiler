# 导读写作规范

本规范约束 `doc/learn/` 下所有“导读”文档。AI agent 新增或修改导读时必须遵守。

目标是让导读服务于两件事：

```text
一边学习新知识
一边验收 AI 产物
```

因此，导读必须小、具体、可验证。不要写成泛泛教程、长篇综述或没有验收入口的总结。

## 1. 文件命名

文件名格式：

```text
NN-主题导读.md
```

要求：

- `NN` 使用两位数字。
- 编号按目录已有最大编号递增。
- 不要复用已有编号。
- 主题必须具体。
- 文件名以 `导读.md` 结尾。

好例子：

```text
04-LocalExecutor导读.md
05-cache-jsonl导读.md
06-per-group-transpose算子导读.md
```

坏例子：

```text
04-一些想法.md
05-优化系统.md
06-总结.md
```

## 2. 标题格式

文档一级标题必须和文件名主体一致：

```md
# NN-主题导读
```

例如：

```md
# 03-count-expert-num-tokens 算子导读
```

标题下面必须写日期：

```md
日期：2026-06-23
```

## 3. 开头必须说明目标

每篇导读开头必须说明：

- 本文解释什么对象。
- 读完应该能看懂什么。
- 它和当前项目验收有什么关系。

推荐格式：

```md
本文解释 `<对象>`。目标是让你能看懂：

- ...
- ...
- ...
```

## 4. 必须区分事实、推断和限制

导读里涉及性能、硬件、真实评测时，必须明确区分：

- 本地 mock/proxy 结果。
- 静态检查结果。
- 真实 Ascend 编译结果。
- 真实 Ascend latency / speedup。

禁止把 `proxy_score` 写成真实性能。

禁止暗示本机可以替代 Ascend A2/A3 真机。

如果只是代码阅读推断，必须写清楚：

```text
这是从代码结构推断的风险，需要真实测试验证。
```

## 5. 推荐结构

不同导读可以按对象调整，但默认使用下面结构。

### 5.1 工具/模块导读

适合 `LocalExecutor`、`cache.py`、`audit_dataset.py`、`run_local_mock.py`。

```md
# NN-主题导读

日期：...

本文解释 ...

## 1. 这个工具解决什么问题
## 2. 怎么运行
## 3. 输入是什么
## 4. 输出是什么
## 5. 核心代码怎么连起来
## 6. 关键数据结构
## 7. 人工验收看哪里
## 8. 当前没做什么
## 9. 下一步小单元建议
```

### 5.2 算子导读

适合 `_count_expert_num_tokens`、`_per_group_transpose` 等 Triton 算子。

```md
# NN-算子名 算子导读

日期：...

本文解释 ...

## 1. 命令参数和算子对象
## 2. 这个算子要做什么
## 3. 输入输出语义
## 4. 测试文件怎么验证它
## 5. wrapper 怎么工作
## 6. Triton kernel 怎么工作
## 7. baseline 算法特点
## 8. seed variant 或候选版本风险
## 9. 当前 mock 产物是什么
## 10. 以后验收这个算子的重点
## 11. 一句话总结
```

### 5.3 验收报告导读

适合 `manifest.json`、`run_report.md`、`dataset_audit.md`。

```md
# NN-主题导读

日期：...

本文解释 ...

## 1. 这个报告回答什么问题
## 2. 怎么生成
## 3. 每个字段是什么意思
## 4. 哪些字段是 mock/proxy
## 5. 人工验收时先看哪里
## 6. 当前格式的不足
## 7. 下一步小单元建议
```

## 6. 必须包含验收入口

每篇导读必须至少包含一种验收入口。

可以是命令：

```bash
python -m unittest discover -s tests -v
python scripts/audit_dataset.py --input-dir ... --output-dir ...
python scripts/run_local_mock.py --input-dir ... --output-dir ...
```

也可以是人工查看入口：

```bash
sed -n '1,160p' output/mock/run_report.md
python -m json.tool output/mock/manifest.json | sed -n '1,120p'
sed -n '1,120p' path/to/source.py
```

导读必须说明：

```text
看这些输出时重点验收什么。
```

## 7. 必须写“当前没做什么”

如果导读对象是 mock、骨架、静态工具或占位接口，必须明确未实现范围。

例如：

```text
当前没有真实 LLM。
当前没有真实 Triton 执行。
当前没有 Ascend 编译。
当前没有真实 latency。
当前没有真实 speedup。
```

这能防止后续 AI 或人把骨架产物误读成真实能力。

## 8. 下一步只能建议一个小单元

文末可以建议下一步，但只能建议一个小单元。

好例子：

```text
下一步建议：给 manifest 增加 unique_candidate_count，避免人类误解 candidates=6。
```

坏例子：

```text
下一步可以接 LLM、接远程 Ascend、做模拟器、加可视化、训练模型、重构框架。
```

## 9. 写作风格

要求：

- 直接。
- 具体。
- 少用抽象口号。
- 多用小例子。
- 解释术语时先给白话含义。
- 命令和路径用代码块。
- 不要写营销式总结。
- 不要把不确定的性能判断写成事实。

## 10. AI 修改规则

AI agent 修改 `doc/learn/` 时必须：

1. 先读取 `doc/learn/README.md`。
2. 先读取本规范。
3. 检查现有最大编号。
4. 避免重复编号。
5. 在最终汇报里说明新增/修改了哪篇导读。
6. 提供人工验收入口。

如果只是在对话中讨论学习内容，不一定要写文件。

如果用户要求“写成报告”或“放入 doc/learn”，必须按本规范落地。
