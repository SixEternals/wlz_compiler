## 1. 先看结论

### 1.1 赛事构成

本批资料覆盖两类赛道：

| 类别 | 资料中覆盖的主题 | 初赛核心目标 |
| --- | --- | --- |
| 编译系统实现赛道 | SysY2026 综合编译器 | 在 ARM 或 RISC-V 目标上正确编译并优化 SysY2026 程序 |
| 编译系统挑战赛道 | 8 个主题：Triton 进化优化、Triton-Ascend 算子、AscendNPU IR 融合、动态算子图、Java 虚拟线程、仓颉数据竞争、仓颉范围分析、LoongArch BOLT | 在指定编译器/中间表示/运行时/硬件边界内取得功能正确和性能优势 |

> **本仓库主赛题的平台结论**：基于进化算法的 Triton 自动优化系统最终运行和计分在华为昇腾 Ascend NPU 上完成，官方目标为昇腾 A2/A3，不是 NVIDIA CUDA/GPU。Triton-Ascend 是该赛题的底层编译运行依赖，但“基于 Triton-Ascend 构建昇腾亲和算子”仍是另一个独立赛题，不能混淆交付边界。

### 1.2 所有参赛队都应提前准备的交付物

- 可被赛方平台获取、构建和运行的完整源码或补丁。
- 设计说明文档：技术思路、系统/模块结构、实现细节、功能与性能结果、对比分析、瓶颈与解决方案、创新点。
- 挑战赛各主题初赛均要求不超过 5 分钟的 MP4 作品介绍视频；实现赛技术方案正文未单列该视频要求，应以平台通知为准。
- 第三方代码、知识产权、开源组件和人工智能生成代码的使用说明。
- 赛后按组委会要求公开代码和文档。

### 1.3 最重要的合规红线

1. 按赛题规定的层级和接口实现，不要修改被明确锁定的算法源码、测试程序或调用方式。
2. 不得针对特定测试用例硬编码、探测测评环境或绕过评测；通用 Pass、通用搜索和通用优化才是安全边界。
3. 所有借鉴、第三方 IP、开源协议和 AI 辅助生成内容必须可追溯，并且队员能够解释原理和代码。
4. 挑战赛多份方案以“修改代码重复率超过 20%取消资格”为标准；实现赛方案另规定高度相似超过 50%且无法说明原创性时取消资格。应按更严格的 20% 标准管理团队代码。

## 2. 通用竞赛规则

### 2.1 初赛与决赛

挑战赛通常采用：

- 初赛：客观功能/精度/通过率 + 性能测试。
- 决赛第一阶段：继续优化初赛作品，并加入不公开测试集或新场景。
- 决赛第二阶段：现场答辩，考察团队协作、代码完成度、设计文档、创新性、规范性和现场表达。
- 多数挑战赛决赛权重：客观分 30%、设计文档 20%、团队协作与现场答辩 50%。

例外：

- 实现赛决赛：新功能 20%、新性能 70%、团队协作/设计文档/答辩 10%。
- LoongArch BOLT 决赛：回归 15%、功能 15%、性能 20%、设计文档 20%、团队协作与答辩 30%。

### 2.2 通用提交与知识产权要求

挑战赛技术方案普遍要求：

1. 在初赛和决赛平台提交源码、补丁或可执行交付物，以及 PDF 设计文档。
2. 初赛提交不超过 5 分钟 MP4 介绍视频。
3. 允许使用遵循开源协议的组件，但必须在设计文档和相关源文件头部说明来源、许可证和使用范围。
4. 竞赛平台通常包括代码托管、自动构建/评测系统和指定硬件测试平台；最终结果以组委会复核为准。
5. 赛后按大赛要求公开代码和文档。

### 2.3 AI 辅助和代码可解释性

实现赛方案明确要求：如果使用大模型等 AI 工具生成源码，至少记录：

- 工具名称；
- 生成内容的范围；
- 人工修改、审查和验证情况。

挑战赛方案普遍要求对第三方代码作同样披露；Triton 进化赛另限制评分阶段允许使用的大模型清单。无论赛题是否明确要求，建议统一维护 `NOTICE/THIRD_PARTY.md` 和 `AI_USAGE.md`，并在设计文档中引用。

### 2.4 不得做的事情

- 针对特定测试用例删除代码、硬替换 IR、写死输入特征或只优化公开样例。
- 探测测试用例特征、测评环境行为，恶意干扰环境或绕过接口/沙箱规则。
- 把未经理解的第三方或 AI 生成代码直接提交。
- 伪造、篡改测试数据或测试结果。

实现赛还规定：若代码与开源项目、其他队伍或受版权保护代码高度相似超过 50%，且不能给出合理原创/引用说明，可取消资格；挑战赛方案一般直接使用“修改代码重复率超过 20%取消资格”的门槛。

## 4. 编译系统实现赛道

来源：[实现赛道技术方案](<sources/official_compiler2026_archive/compiler2026-main/2026年全国大学生计算机系统能力大赛-编译系统设计赛-编译系统实现赛道技术方案.pdf>)。

### 4.1 目标与语言

- 从零设计并实现综合性编译系统，体现编译技术、操作系统和计算机系统结构能力。
- 编译器可用 C、C++、Java 或 Rust 开发，并须能在 x86 服务器 Ubuntu 24.04（64 位）环境完成构建。
- 输入语言为 SysY2026：语法/语义主要参考 C，包含全局变量、自定义函数、`int`/`float` 多维数组、向量、赋值、表达式、语句块和常见控制流。
- 编译器需要具备词法、语法、语义分析、目标代码生成、优化、错误识别/定位/处理能力。

### 4.2 目标平台和调用约定

**ARM 路线**

- 输出 64 位 ARMv8-A 汇编。
- 目标板：赛灵思 XCZU15EG，ARM Cortex-A53，Ubuntu 22.04。
- 汇编/链接：`gcc 11.2.0`，`gcc -march=armv8-a`。
- 可执行编译器统一命名 `compiler`；功能：`compiler testcase.sysy -S -o testcase.s`；性能：追加 `-O1`。

**RISC-V 路线**

- 输出 64 位 RISC-V 汇编，遵守较大地址空间约定（GCC `-mcmodel=medany`）。
- 目标为 64 位 FPGA BOOM v3 软核，RV64GC，初赛不得使用 SIMD。
- 汇编/链接：`gcc 13.3.0`，`gcc -march=rv64gc`。
- 编译器调用形式同上，性能测试追加 `-O1`。

### 4.3 初赛/决赛评分

- 功能用例：每个测试点按通过比例计分，所有功能用例得分取平均。
- 性能用例：每个用例以全体队伍最短运行时间为 100 分，其余按“最短时间/本队时间”计分，最终取几何平均。
- 初赛总分：功能 50%、性能 50%。
- 决赛：新功能 20%、新性能 70%、团队协作/设计文档/答辩 10%。决赛会公布新测评用例和可能的语言/平台变化。

### 4.4 提交与等级认定

- 初赛提交完整工程（必须含全部源代码）和设计/实现文档，平台至少留有一次完整功能或性能测评记录及有效成绩。
- 允许 Lex、YACC、Bison、JavaCC、JavaCUP、ANTLR 等通用生成器；禁止直接使用 GCC、LLVM 及其裁剪源码来构造编译器。
- 等级证书：一级要求必过功能用例且性能分不低于 90；二级要求必过且性能分 40 至 90；三级要求功能分不低于 60；入门级要求能编译并通过至少 5 个功能用例。
- 性能等级认定另以决赛性能用例相对 GCC 11.2.0 `-O2` 的结果计算。

### 4.5 构建与硬件基线

| 项目 | 参数 |
| --- | --- |
| 构建服务器 | AMD64，8 GB，Docker Ubuntu 24.04 |
| C/C++ | LLVM/Clang 18；C `clang --std=c11 -O2 -lm`；C++ `clang++ --std=c++17 -O2 -lm` |
| Java | OpenJDK 24；主类 `Compiler.java`；`javac -encoding utf-8` |
| Rust | `rustc 1.85.0`；`rustc -O2` |
| ARM 板 | Cortex-A53 4 核，L1D/L1I 各 32 KB，L2 1 MB，共 4 GB DDR4；隔离核 2、3用于计时 |
| RISC-V 板 | BOOM v3，50 MHz，双发射乱序，2 GB；IEEE754 FPU；初赛无 SIMD |

## 5. 挑战赛详解

### 5.1 基于进化算法的 Triton 自动优化系统（重点）

来源：[中文方案](<sources/official_compiler2026_archive/compiler2026-main/2026年全国大学生计算机系统能力大赛编译系统设计赛-编译系统挑战赛-基于进化算法的Triton自动优化系统-技术方案.pdf>)、[英文方案](<sources/official_compiler2026_archive/compiler2026-main/Huawei_BiSheng_Cup-Automatic_Triton_Optimization_System_Based_on_Evolutionary_Algorithms.pdf>)。

**任务边界**

- 在赛方提供的 agent 框架、安装环境和接口上实现进化算法，自动搜索/变换 Triton 算子。
- 必须使用赛方环境和接口，不能改变接口调用方式；特殊依赖只能通过 `pip` 安装并说明。
- 输入是赛方提供的 Triton 代码库；不得手工修改 Triton 代码。
- 可以改进 agent 自身模块、工具和 multi-agent 协作，但 multi-agent 的 token 消耗总和计入预算。
- 每个算子评测最多 20 分钟或 200,000 token，任一上限先到即停止；评分时不指定某个模型，使用队伍默认模型。
- 初赛 agent 每队拟分配 300 元 token 额度，决赛追加 300 元，实际额度以最终方案为准，仅供开发使用。

**Ascend 平台定位（官方硬要求）**

该赛题不是在普通 CUDA Triton 环境中计分。官方中文方案明确给出的运行环境是：

| 层级 | 官方要求/用途 |
| --- | --- |
| Host CPU | 鲲鹏 920 ARM |
| 加速器 | 昇腾 Ascend A2/A3 NPU |
| 操作系统 | openEuler |
| Triton 实现 | 华为开源 Triton-Ascend：<https://gitcode.com/Ascend/triton-ascend> |
| 正式测试 | 昇腾 A2/A3 服务器，由竞赛评测系统进行编译、正确性和性能测试 |
| 开发调试 | 华为 HiDevLab：<https://hidevlab.huawei.com>，申请昇腾 IDE 环境时用途填写“华为毕昇杯挑战赛”，并提供队伍和赛题名称 |

官方没有说明向参赛队发放实体板卡；现有资料指向竞赛平台和 HiDevLab 的远程/云端环境。具体 CANN、驱动、固件、Triton-Ascend commit 和 profiler 版本在本地赛题 PDF 中没有固定，不能自行假设或写死，应以评测环境通知为准。

**Ascend 端到端编译与评测链路**

结合官方赛题方案和仓库现有的[研究与实施总计划](<2026-Triton进化优化研究与实施总计划.md>)，正确的平台关系是：

```text
赛方原始 Triton 算子
        |
        v
给定 agent 接口
        |
        v
进化搜索：选择 / 变异 / 交叉 / 失败反馈 / 预算控制   <- 本队主要交付
        |
        v
最多 5 个候选 Triton Python 算子
        |
        v
官方编译、正确性和性能执行接口
        |
        v
Triton Python -> TTIR -> Linalg IR -> AscendNPU IR/下游 IR
        |
        v
毕昇/昇腾编译链 -> Ascend 设备二进制 -> A2/A3 NPU
```

这里应严格区分：

- 本队的创新和提交主体是 **agent 与进化搜索系统**。
- Triton-Ascend、AscendNPU IR、毕昇编译链和 A2/A3 是 **底层基础设施/目标平台**，不是本赛题要求参赛队重写的编译器。
- 不应为了本赛题直接修改 Triton-Ascend 或 AscendNPU IR，也不能绕过赛方统一接口；这样会越过赛题边界。
- 只有官方接口实际暴露了 TTIR、Linalg IR、AscendNPU IR 或 profiler 字段时，agent 才能把它们用于反馈。不能因为底层工具支持 dump/profiling，就假设比赛接口一定允许访问。

**哪些结论必须在真实 Ascend 上取得**

| 本地可完成 | 必须在 Ascend A2/A3 或官方评测完成 |
| --- | --- |
| Python/Triton 静态语法和 AST 检查 | Triton-Ascend 真实编译是否成功 |
| 函数签名、装饰器、launch contract 检查 | 全部 shape/dtype 的正确性与误差检验 |
| 进化策略、候选去重、缓存、预算和 provenance | A2/A3 真实执行时间、性能排序和官方 speedup |
| LLM 输出清洗、搜索流程和本地 mock | 真实编译错误、运行时错误和可用 profiler/IR 反馈 |

CUDA/NVIDIA 上的 Triton 结果最多只能验证通用 Triton 编程或 agent 流程，不能作为 Ascend 正确性、A2/A3 延迟或比赛性能分的证据。本地 proxy 只能标为 `local_score`/`proxy_score`，不能写成官方 `speedup`。

**功能与性能**

- 统一接口最多返回 5 个算子版本。
- 至少一个版本成功编译并通过全部测试才有功能分 100；不能完全通过则功能分 0；与原算子完全相同不得分。
- 初赛 50 个测试 case，功能/误差通过率 30%，性能 70%。
- 正式功能与性能均通过统一执行接口落到昇腾 NPU；正确性是硬门槛，只有完全通过功能测试的候选才会在 A2/A3 上计算性能分。
- 仅功能完全通过的版本进入性能评测。性能加速比：

  `speedup_ratio = max(baseline_time / optimized_time - 1, 0)`

  100 ms 优化到 50 ms 时加速比为 1.0，对应 100 分；性能分上限 200 分；多个通过版本取最高分。

- 决赛在公开 50 个 case 外增加 50 个不公开 case；客观分 30%、设计文档 20%、团队协作/答辩 50%。

**比赛样例：50 个基线 kernel 与 21 个提交算子**

来源：[官方接口能力审计](<2026-Triton官方接口能力审计.md>)、[官方评测纠错报告](<2026-Triton官方评测四类问题纠错报告.md>)，以及赛题页指定的[官方基础框架](<https://gitcode.com/lirui_ryan/Evolutionary-Algorithm-Based-TritonAscend-Optimization>)固定提交 `ef8c3bbc7bae6bdfa2af61722f9da14fd8ea5781`。

这里有三个容易混淆的数量口径：

| 口径 | 数量 | 准确含义 |
| --- | ---: | --- |
| 2026 年 4 月技术方案 | 50 个初赛 test case | 方案层面的公开测试规模表述 |
| 官方框架 `baseline/baseline.json` | 50 个唯一 kernel、每个 3 个 case，共 150 条基线记录 | 文件记录了 50 个 kernel 的 `tc1/tc2/tc3` 基线耗时 |
| 官方框架实际 `datasets/` | 21 个 kernel 目录 | 随框架公开源码、seed variant 和一个公开测试脚本的可操作样例 |
| 官方提交平台观测 | 21 个提交算子、每个 3 个任务，共 63 个任务 | 页面出现 `提交 21/21`、`AC(x/63)`；这是当前提交口径 |

因此不能把 50 理解为“仓库内有 50 份完整公开源码”，也不能理解为“参赛队可从 50 个中任意挑 21 个”。固定官方框架中只有下面 21 个算子带有随仓数据目录，当前平台按这 21 个算子接收和统计提交。

**21 个算子的提交输出契约**

- 提交单位是 21 个 kernel 槽位，不是“全场只能交 21 份候选代码”。
- 每个 kernel 的 agent 最多返回 5 个候选版本；至少一个必须是非原样、成功编译且通过全部测试的候选。
- 官方 `save_results()` 会为每个 kernel 写出 `<kernel>_best.py`、`<kernel>_v1.py` 至 `<kernel>_v5.py`（实际数量不超过 5）和 `<kernel>_stats.json`。
- `_best.py` 是最佳候选的便捷输出，通常来自 Top-5，不应当作第 6 个独立候选；`stats.json` 也不是候选。
- 整体结果由外层流程汇总为 `output.zip`；目录名、kernel 名和文件命名必须与这 21 个官方槽位精确一致。
- 平台的 63 个任务来自 `21 kernel × 3 task`。一个 kernel 只有三个任务全部通过，才满足技术方案的“通过所有测试”功能门槛；partial 不能当作该 kernel 完整功能通过。

### 5.3 基于 AscendNPU IR 的 NPU 自动融合代码生成与调优

来源：[中文方案](<sources/official_compiler2026_archive/compiler2026-main/2026年全国大学生计算机系统能力大赛编译系统设计赛-编译系统挑战赛-基于AscendNPU_IR的NPU自动融合代码生成与调优-技术方案.pdf>)、[英文方案](<sources/official_compiler2026_archive/compiler2026-main/Huawei_BiSheng_Cup-Automatic_Fusion_Code_Generation_and_Optimization_for_NPU_Based_on_AscendNPU_IR.pdf>)。

### 5.5 Java 虚拟线程实现机制优化

来源：[中文方案](<sources/official_compiler2026_archive/compiler2026-main/2026年全国大学生计算机系统能力大赛编译系统设计赛-编译系统挑战赛-Java虚拟线程实现机制优化-技术方案.pdf>)、[英文方案](<sources/official_compiler2026_archive/compiler2026-main/Huawei_BiSheng_Cup-Optimization_of_Java_Virtual_Thread_Implementation_Mechanism.pdf>)。

## 6. 统一精度与性能测量要点

以下规则主要出现在 Triton-Ascend 和 AscendNPU IR 方案附件中：

### 6.1 整数

- golden 为 CPU 计算结果。
- 通过标准为二进制逐元素一致。

### 6.2 浮点

- FP16/BF16 输入先转 FP32 计算，输出 FP32；FP32 直接以 FP32 计算。
- golden 出现 Inf/NaN 时该用例无效。
- NPU 结果为 Inf/NaN：FP16 需检查 FP32 golden 是否超出 FP16 表示范围；若未超出则失败。FP32/BF16 在 golden 非 Inf/NaN 时出现 Inf/NaN，失败。
- golden 绝对值大于等于 1：相对误差不超过阈值；小于 1：绝对误差不超过阈值。

常见定义：

```text
RE = (actual - golden) / (golden + 1e-7)
AE = |actual - golden|
```

阈值 `err`：

| 精度 | 累积计算次数 | 阈值 |
| --- | --- | --- |
| FP16 | < 2048 | `2^-8` |
| FP16 | >= 2048 | `2^-7` |
| BF16 | < 2048 | `2^-7` |
| BF16 | >= 2048 | `2^-8` |
| FP32 | < 2048 | `2^-11` |
| FP32 | 2048 至 < 16384 | `2^-10` |
| FP32 | >= 16384 | `2^-9` |

“计算次数”通常是一次累加参与的元素数量，例如向量长度或 reduce 维度。

### 6.3 AscendNPU IR 编译器问题处理

若遇到精度异常，方案附件建议：

1. 试验 `inject_barrier_all=[True|False]`；若 True 通过而 False 不通过，可记录为编译器问题，按方案默认配置通过功能考察。
2. 在其他支持 Triton 的平台复现；若其他平台通过，记录复现步骤并反馈，方案允许默认通过该配置的功能考察。

## 7. 软硬件与本地调试参考

### 7.1 ARM Cortex-A53 参考参数

来源：[ARM 硬件规范](<sources/official_compiler2025_archive/compiler2025-main/CG-FPGA15EG_ARM_Cortex-A53_MPCore_硬件技术规范.pdf>)。

- XCZU15EG，Cortex-A53，4 核；核心 2、3 用于隔离测评。
- ARMv8-A 64 位；L1 数据/指令缓存各 32 KB；共享 L2 1 MB；DDR4 4 GB。
- 支持标量单/双精度浮点；NEON 为 128 位，支持整数和单精度浮点向量；不支持双精度 NEON 向量。
- `isolcpus=2,3` 会隔离测评核心；多线程优化需处理线程绑定，避免迁移。

### 7.2 RISC-V BOOM 参考参数

来源：[BOOM 硬件方案](<sources/official_compiler2025_archive/compiler2025-main/CG-FPGA15EG_BOOM软核硬件技术方案.pdf>)。

- BOOM v3，RV64GC（RV64IMAFDC），50 MHz，乱序执行、双发射、超标量；内存 2 GB。
- FPU 支持 IEEE754 单/双精度、FMA、比较和转换；初赛无 SIMD。

### 7.3 QEMU 本地调试

来源：[QEMU 本地调试指南](<sources/official_compiler2025_archive/compiler2025-main/QEMU本地调试指南.pdf>)。

- 适用 Ubuntu 22.04+ / Debian；指南使用 `qemu-system-misc qemu-system-arm qemu-utils cloud-image-utils wget`，并配合 `opensbi u-boot-qemu qemu-efi-aarch64`。
- AArch64：Ubuntu Noble ARM64 cloud image，扩容至 15G，使用 QEMU EFI 启动；虚拟机内安装 `gcc gdb`。
- RISC-V：Ubuntu 24.04.2 RISC-V 镜像，扩容 5G，使用 `qemu-system-riscv64` 和 U-Boot 启动；虚拟机内安装 `gcc gdb`。
- 本地调试流程：编译时加 `-g`，使用 GDB 在 `main` 等位置断点。QEMU 只能验证指令/运行逻辑，不能替代赛方真实板卡性能测评。

## 8. 2025 资料的定位：只作历史参考

来源：[2025 代码自动混精方案](<sources/official_compiler2025_archive/compiler2025-main/2025全国大学生计算机系统能力大赛-编译系统挑战赛-代码自动混精-技术方案.pdf>)。

该资料不是 2026 赛题要求，但对 LLVM Pass 和 ARM 性能实验有参考价值：

- 任务是 LLVM Pass 层自动混合精度优化双精度求解器；初赛 200 个矩阵，功能 40%、性能 60%。
- 重点流程为矩阵生成、LU 分解、GMRES 补偿和误差校验；通过 `pragma AutoMxPrec` 标识混精优化范围。
- 公开矩阵配置曾使用 `iseed=1`、`n=128..5302` 线性递增，决赛最大矩阵维度不超过 30000（这是 2025 方案的历史参数，不可直接用于 2026）。
- 可借鉴的工程思路：插桩、变量/循环/函数级搜索、误差回归、性能与精度联合门控。
