## 2. 计分公式与"均值陷阱"（务必先读懂）

### 2.1 单算子得分

`kernel_score = 100 × clamp(baseline_time / current_time − 1, 0, 2)`

- speedup=2.0（即 3× 快）→ 200 分（上限）
- speedup=0.48 → baseline/current=1.48，即比 baseline **快 48%** → 47.76 分
- speedup=0 → 与 baseline 持平或更慢（被 `max(·,0)` 截到 0）→ 0 分

**注意方向**：manifest 里的 `local_ratio` 是 `candidate/baseline`（越小越快）；官方 `avg_speedup` 是 `baseline/current − 1`（越大越快）。两者互为倒数关系。local_ratio 0.16（chunk_cumsum）≈ 本机快 6× ≈ 官方封顶 200。local_ratio≈1.0 ≈ 无提速 ≈ 官方≈0。

### 2.2 总分近似是"均值"，不是"求和"——这是关键

本轮 19 个计入算子得分求和 ≈ **612.83**，`612.83 / 19 = 32.25`，与页面 `avg_speedup=32.25` 完全吻合；`总分=32.00`（系数 1.00）也贴着这个均值。

**推论（一个数据点，需在官方多轮验证，但信号很强）：总分是"有≥1个通过任务的算子"的得分均值。** 若成立，则：

- **抬"已计入、分数中等"的算子（第一部分）= 分子增、分母不变 = 纯涨。** 最安全。
- **把 0/3 失败算子修成"通过但低分"（第二部分）可能拉低均值**：分母 +1，分子只 +小值。例：修 selective_scan 到 3/3 但只得 10 分 → `(612.83+10)/20 = 31.14 < 32.25`，**总分反而降**。它只在得分 > 当前均值(32.25)时才抬总分——而这些硬骨头算子几乎不可能。
- **但第二部分能抬"通过率 30%"那一档**（54/63 → 更高）。初赛 = 通过率 30% + 性能 70%。所以修失败算子帮的是通过率分量，可能伤性能均值分量。二者如何合成为最终名次 = **未知**，需确认。

⚠️ Codex 必读：不要无脑"修失败算子提分"。先确认平台总分到底是均值还是求和、以及通过率分量如何并入最终分。若是均值，优先级是"抬中段" > "修失败"。

## 4. 唯一结构上非负的杠杆：多槽位 max() + 准入组装器（最高优先工程）

### 4.1 原理

官方规则："每算子最多 5 个候选版本，多个通过版本**取最高分**。" 既然我们判断不准哪个候选官方快，就每个算子塞多个不同候选，让平台挑官方最快的那个。**这是对"本机≠官方"不确定性的正确对冲，数学上只涨不跌**（前提：不覆盖已通过的 v1）。

### 4.2 打包器的硬约束（`scripts/build_official_agent_batch_smoke.py`）

- 槽位 1–5；`v1 ≠ v2` 改动类型必须不同（:660-670）。
- `v3_functional_fallback_only` 候选被强制锁在 slot 3（:630-634）。b98 就是这种。
- 候选等于 baseline hash → 直接拒（:603-606）。
- **每个进包候选必须有完整准入块**：manifest 里的 `correctness_evaluation` + `holdout_evaluation` + `decision`，且 `require_current_admission=True`（:436-452）。`corr=None` 的备选一律被拒。
- 五候选互不相同、都不等于 baseline；去重按 candidate_id 和 sha256（:362-365）。

### 4.3 真正的堵点：没有"准入组装器"

- 磁盘上除各算子已提交的 v1，其余备选几乎全是 `corr=None`。
- 写准入块的 `scripts/generate_official_candidates_batch.py` 是 **LLM 生成导向**（参数是 token 预算/max-new-calls），**不给已 materialize 的候选补准入块**。
- b98 的准入 manifest 是**手工拼**的（holdout case + correctness + paired + 手工组装带 SHA 的准入块），证据在 `output/overfit-probes/count-expert-case2/`。
- **⇒ 最高杠杆的一件事：写一个可靠的"准入组装器"脚本**，输入 = 候选 + 真机 correctness/holdout/paired 证据，输出 = 打包器认的准入 manifest（自动填 artifact_path/sha256/decision 等）。
  - **可安全验证**：b98 是已知正确的准入 manifest。让组装器从 b98 的证据重新生成一遍，与 b98 现有字节逐字节比对，一致才敢用到新候选。**有黄金参照，不是盲拼。**
  - 做出来后：今天能给 count_expert（3 个已验证备选）补多槽位；决赛前可复用给所有算子做多槽位对冲。

### 4.4 组装器需要的证据流水线（每个新候选）

1. `scripts/run_local_ascend_correctness.py`（**已完成 today 的 5 个**）— 用 `/usr/local/python3.11.15/bin/python3`（含 torch_npu），`--output` 必须在仓库根内（不能 /tmp）。
2. holdout case 生成（参考 count-expert-case2 的结构）。
3. `scripts/run_local_ascend_paired_benchmark.py` — 配对性能。
4. 准入组装器（**待写**）— 生成 manifest 准入块。
5. `scripts/build_official_agent_batch_smoke.py` 多槽位重打包。
6. **shape 门复验**（见第 5 节风险）。

## 7. 提交模型与合规（来自 `doc/2026-08-05提交模型与合规边界核查报告.md`）

- 线上计分 = **冻结候选 ZIP**（根目录含 `output/`），平台**不运行** agent 的 main.py，**人工上传**。
- 合规硬规则：候选必须由 agent 经统一接口产生，**不允许评测前人工改写 Triton 代码**。离线生成候选可以，但每个候选要能追溯到合规的 agent/materialize 调用；materialize 的"精确文本改写"是否算合规改写，**存疑，需向赛方确认**。
- 提交是**用户手动**操作，不可逆、公开计分。任何新 ZIP 都应与 32 分那个**并存、不覆盖**，等确认平台"取最高/取最后"再决定交哪个。
